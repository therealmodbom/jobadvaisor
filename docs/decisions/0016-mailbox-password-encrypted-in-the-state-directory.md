# 0016. Mailbox password encrypted in the state directory, with the key from the secret configuration

## Status

Accepted, 2026-11-23.

## Context

Issue [#58 (Intake: read job alert mails from a configured mailbox)](https://github.com/therealmodbom/jobadvaisor/issues/58) lets the user enter an IMAP password in the web UI. The app must send that password in plain text to the IMAP server at every login, so a hash cannot store it. The stored form has to be decryptable, and the key has to be somewhere the backend can reach.

The backend runs on any machine, usually Linux without a desktop session. The macOS Keychain the app already reads (`settings.py`) holds only a local test environment's secrets. Secrets reach the container from the host's secret file (mode 600) as environment variables. The state directory (`STATE_DIRECTORY`) is a local, persisted volume outside the data repository. The data repository is pushed to a backup remote. The repository is public, so the mechanism must work on any deployment, using only the configuration paths the app already has.

## Decision

The app encrypts the password with a symmetric key and writes only the ciphertext to a file in the state directory. The key is a secret setting (`MAILBOX_KEY`), read like every other secret: from the Keychain on macOS, the environment, or `.env`, and in the container from the host's secret file. Without a key, the app stores no password.

Threats covered and not covered:

- A copy of the state directory or its backup alone reveals nothing.
- The data repository and its remote never hold the password.
- An attacker with root on the backend machine can read the key from the process environment or memory. This holds for every option below.

## Alternatives considered

- **The password itself in the secret file, set by hand on the host.**
  - Simplest, and no encryption is needed.
  - Rejected, because the issue requires that the web UI sets the password.
- **A key file generated by the app on first use.**
  - Saves the setup step.
  - Rejected, because the app would write the file next to the ciphertext in the state volume, and a copy of that volume would then reveal the password.
- **A desktop keyring (macOS Keychain, Linux Secret Service).**
  - Rejected as the mechanism: the Secret Service needs a desktop session, which the server does not have.
  - The macOS Keychain still works for the key itself, as for every secret.
- **The key from the host's credential store (`systemd-creds`, bound to the machine or its TPM).**
  - Stronger, because a copied disk alone is not enough.
  - Rejected for now: it exists only on systemd hosts, is harder to reach from a container, and would add a setup only some deployments can follow. It is a possible later add-on for the key's source.
- **A passphrase typed at every start.**
  - The only option that also resists root on a machine at rest.
  - Rejected: every restart, including the container's automatic one, would need a person.
- **A key file path or Docker secrets for the key.**
  - Rejected: one more configuration path for one setting. The host's secret file already serves every secret.

## Consequences

- Setting up the mailbox needs one generated key in the secret configuration. The README shows the command that generates it.
- Losing or changing the key makes the stored password unreadable. The app says so and asks for the password again. Nothing else is lost.
- The UI and the README recommend an app password, so that a leaked password can be revoked on its own.
- A new dependency: `cryptography` (Fernet: AES in CBC mode with an HMAC).
