# Design

## Context

See proposal.md for motivation. Facts the design relies on (read from the code):

- `create_app` mounts `frontend/dist` at `/` after the API routes when `index.html` exists, and the frontend calls the API with relative paths. One uvicorn process serves UI and API on one port; there is no separate frontend server, no CORS, no second container.
- `REPOSITORY_ROOT` is `Path(__file__).parents[2]` of `settings.py`, and `FRONTEND_BUILD` hangs off it. The image must keep the repository layout and install the backend **editable**, otherwise the package lands in `site-packages` and the build is not found.
- Settings come from the Keychain (absent on Linux, the lookup returns `None`), the environment, `.env` and `local.env` in `REPOSITORY_ROOT`. The image has neither file; Compose supplies the environment. No settings change is needed.
- Chromium is launched by Playwright in `intake/fetch.py` (default launch, no sandbox flag set). The image needs the browser and its system libraries.
- The app only writes files into the data repository and never commits (ADR 0001). Run state (checkpoints, vector index) lives under `STATE_DIRECTORY`, one subdirectory per data repository, and rebuilds from the data.
- The target is any Linux server with Docker and Compose that can read and write the data repository's remote with credentials stored on it (an SSH key, a CLI login, a token). `<server>` and `<remote>` below stand for the user's own.

## Goals / Non-Goals

**Goals:**

- One image, one command to update, no public port, persistent data.
- A cutover that loses no pending rating and a restore path that was run once.

**Non-Goals:**

- Anything the proposal lists. No eval: this change touches no LLM-backed behavior, so there is no eval metric or data to name.

## Decisions

**1. One container, one process.** Multi-stage build. Stage one: Node (version from `frontend/.nvmrc`) runs `npm ci` and `npm run build`. Stage two: `python:3.12-slim`, `uv sync --locked --no-dev` into `/app/backend/.venv` (editable, keeps `parents[2]` at `/app`), the built `dist` copied to `/app/frontend/dist`, then `playwright install --with-deps chromium` with `PLAYWRIGHT_BROWSERS_PATH=/ms-playwright`. The process runs as a non-root user and starts `uvicorn --factory jobadvaisor.api.app:create_app --host 0.0.0.0 --port 8710` with one worker (runs and checkpoints are in-process). Frontend and backend share the container because the backend already serves the built frontend; two containers would add a proxy for no gain. The image is large because of Chromium; accepted, it is pulled once per release.

**2. Compose binds to loopback, on a configurable port.** The service publishes `127.0.0.1:${JOBADVAISOR_PORT:-8710}:8710`: the container always listens on 8710 inside, and the host-side port is the setting `JOBADVAISOR_PORT` in the deployment directory's project `.env` (Compose reads it for every command). Changing it needs `docker compose up -d`, which recreates the container with the new mapping (a plain `docker compose restart` keeps the old one), not a new image. The host side is loopback, so a mistaken Compose edit cannot expose the port publicly. Settings: the Compose file sets `DATA_REPOSITORY=/data` and `STATE_DIRECTORY=/state`, reads non-secret settings (models, URLs) from `settings.env` and secrets from `secrets.env` (mode 600, never in the image or the repository), both in the deployment directory. The deployment directory is `/srv/jobadvaisor` with `data/` (the clone), `state/`, the two files, the project `.env` and the Compose file.

**3. Publish the loopback port to the private network with `tailscale serve`.** The worked example in the README is `tailscale serve --bg --https=<https-port> http://127.0.0.1:<port>`, which serves the app at `https://<server>.<tailnet>.ts.net:<https-port>` with the certificate Tailscale issues for that name; an existing entry on port 443 is left alone. Any other setup that forwards a private network to the loopback port (another VPN, a reverse proxy bound to it) works the same, and the README says so. The alternative, publishing on the Tailscale IP in Compose, gives plain HTTP and fails to start the container if Docker comes up before Tailscale; rejected. See [ADR 0009](../../../docs/decisions/0009-container-from-ghcr-behind-tailscale-serve.md).

**4. Release through GHCR.** A workflow on tags `v*` builds `linux/amd64` with `docker/build-push-action` and pushes `ghcr.io/therealmodbom/jobadvaisor` with the tag, and `latest` for non-prerelease tags only (`docker/metadata-action`), using the job's `GITHUB_TOKEN` (`packages: write`). The existing `eval-*` tags do not match. The update on the server is `docker compose pull` then `docker compose up -d` in the deployment directory. The image tag comes from `JOBADVAISOR_TAG` in the project `.env`, so no command needs the variable in front; a prerelease tag does not move `latest`, so while the server runs one, the line names it, and deleting the line switches to `latest` from the first non-prerelease tag on. The repository is public (#44), but GHCR creates a package private on its first push. The repository owner sets it to public once in the package settings (a GitHub web step, no code), and the server then pulls without a login. The image holds no secret and no personal data, so public is safe; the spec requires that. Keeping the package private instead needs a one-time `docker login` with a `read:packages` token entered through a hidden prompt. Building on the server was rejected: every update would compile Node and install Chromium on a machine that may run other services. The release workflow does not retest the tagged commit; it was tested on its branch. A `docker build` job in `ci.yml` (no push) plus a smoke check catches a broken Dockerfile before the tag, not at it.

**5. Data on the server as a clone of the repository's remote.** `/srv/jobadvaisor/data` is a clone of the data repository's remote (`<remote>`, the origin), mounted at `/data`. The remote stays the shared point: other machines, or an external tool (ADR 0001), may push to it, so the server is not assumed to be the only writer and nothing enforces it. The container user owns the working tree so the app can write; git on the host runs as root with `safe.directory` set for that path, so git objects are root-owned and the app never needs to touch `.git`. Until #63, the user commits and pushes by hand on the server, with the service running. Nothing more is expected, since only the app writes today. If the push is rejected because the remote has changes the server lacks, the documented recovery applies. To meet "a sync never races the app", it stops the service for its whole duration, so no rating lands mid-checkout and no request reads a half-merged file; #63 meets the same requirement by holding the app's writes back instead. The recovery: `docker compose stop`, commit the app's pending changes, fetch, rebase (or merge) the remote's changes onto them, push, `docker compose up -d`. A fast-forward or non-overlapping change goes through. A conflict leaves git stopped with the file named and the service stays stopped: the user either resolves it in the working tree and continues, or aborts (`git rebase --abort`), which restores the exact pre-sync state, then starts the service. Both writers' data survives because the app's changes are committed before the remote's are applied, so the abort path loses nothing. The service does not start by itself afterwards (`restart: unless-stopped` keeps a manual stop), so the recovery ends with `docker compose up -d`. The cost is downtime during a rare recovery, acceptable for one user. The server does not auto-resolve, and the sync never forces a push. An unpushed rating exists only on the server until the push. Cutover order: confirm the existing local data repository is clean and pushed, clone on the server, start the container, verify, then stop writing to the local copy. No migration code: the data format is unchanged.

**6. Restore.** Documented as: stop the service, move `data/` and `state/` aside, `git clone` from the remote into `data/`, set the commit identity again (it lives in the clone's config), `chown` to the container user, start the service; the state rebuilds from the data (ADR 0004). Tried once on the server before the change ends, against the real remote, comparing the file list with the moved-aside copy.

**7. Verification is a walkthrough, not a unit test.** The container passes a real client sequence: the UI loads from two devices over the private network, add a posting, score it, rate it, reload and see the rating, restart the container and see it persist, then the restore. The Dockerfile smoke check in CI covers only what a test can: the build exists at the expected path and Chromium launches in the image.

## Risks / Trade-offs

- **No login, the private network is the only control** → the host side is loopback and the private-network entry is the single way in; anyone on that network reaches the app. Acceptable for one user's devices. A shared network would need access rules first.
- **Unpushed data lives only on the server until #63** → the README states the push command; a lost server loses the unpushed ratings. Fixed by #63, not here.
- **Concurrent writers** (ADR 0001: no concurrent writers) → the app serves one user from one instance, and the remote's other writers go through git, which reports a conflict instead of overwriting. The recovery runs with the service stopped (decision 5), so the app and git never write the working tree at once.
- **A commit while the app writes** → the normal commit runs with the service up and could capture a file mid-write; the next commit repairs it. #63 excludes it by design.
- **The app is unreachable during a recovery, without an explanation** → the container is down, so the private-network entry has nothing to forward to and the browser shows a connection error, and it stays down until the user runs `docker compose up -d`. No maintenance page exists. Acceptable for a rare recovery the user started themselves; a static notice page is possible later, and #63 replaces this with a banner in the running app.
- **Syncing stays manual until #63** → the server and the remote drift apart until the user pushes, and a conflict is found only when a push is rejected. #63 adds the scheduled sync and the notice.
- **Image size and cold pull** → Chromium dominates; accepted, pulled once per release.
- **Playwright default launch in a container** → it runs without the Chromium sandbox, so a malicious page could escape more easily than in a normal browser. Mitigated by the non-root user and by fetching only URLs the user submits.
- **A public image is downloadable by anyone** → it holds only public code and a browser; the CI smoke check searches it for secret and data files.
- **CPU architecture** → the workflow builds `linux/amd64` only. An ARM server needs `linux/arm64` added.
