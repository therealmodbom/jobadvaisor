# Design

## Context

See proposal.md for motivation. The existing `feature_extraction` eval (`evals/feature_extraction.py`) runs one model from `EXTRACTOR_MODEL`, scores per-field accuracy against `fixtures/evals/feature-extraction/expected.json` (demo persona only), meters cost per posting through `evals/cost.py` and measures no latency. The extraction itself is `extract_features(posting, features, model)`, used by the triage graph, the agent tool and the logistic-regression eval, so extractor quality decides what those see. `chat_model(role, settings)` builds the client from one (model, base URL) pair per role.

## Goals / Non-Goals

**Goals:**
- One command that evaluates one extraction approach per run and stores the run, so the history shows how the approach performs over time.
- A ground truth that grows from comparing runs, with the user judging only the cases on which runs disagree.

**Non-Goals:**
- No change to `extract_features`, its prompt or the feature set. The runs get the same input.
- No use of DeepEval's hosted report store, and no judge-model metric: the checks are exact comparisons.
- No parallel runs: latency per posting is the wall-clock time of one sequential call, and parallel calls would distort it.

## Decisions

**Eval for this behavior.** The benchmark is itself the eval of the extractor. Metrics: *accuracy* against extraction labels (labelled cases only, failed call = wrong) and *agreement* between compared runs (share of postings with equal values for a feature, over postings every run answered). Data: the stored postings of the chosen data repository (the demo persona in tests). Accuracy is computed by a DeepEval metric (see below). The benchmark has no LLM-backed behavior of its own: the extractor is the system under test, and judging a disagreement is the user's act. Tests stub the models and never make a paid call.

**A run is one model; comparison is a separate step on stored runs.** The history then follows the extraction approach, and comparing models is a query over it, done by the command (`--compare`) or by hand or script. Alternative: one run executes several candidates from a configured list, rejected because it ties history to a fixed set of competitors, needs a candidate list file with identity rules, and a run per model is just as easy to start. The model is `EXTRACTOR_MODEL` by default, or `--model` and `--base-url` for one run. So there is no candidate file, and no model names of the user's choosing sit in this public repository.

**What a run stores.** The JSONL record holds the parameters that define the approach: model, base URL, a hash of the extraction instructions (`INSTRUCTIONS`), a hash of the feature set that was extracted, and the app's git commit (null outside a git checkout), plus figures only. The extracted values go to `benchmark/runs/<run id>.json` in the same state directory, because a comparison needs them and a record must hold none (privacy: the records are the file most likely to be shared). The run ID is the UTC time stamp and the model name made file-safe. Alternative: re-extract on every comparison, rejected because it pays twice and the model may answer differently the second time.

**Extraction labels in their own file (`extraction-labels.json`).** Shape: `{schema_version, min_accuracy?, labels: {<posting id>: {<feature id>: value}}}`. Alternative: inside `policy-pack.json`, rejected because that holds rules the user edits by hand, while this file is written by the command and grows with every settled comparison. It is an optional entity with a schema generated from the Pydantic model (ADR 0006). A label naming a posting or a feature that does not exist fails the load. Label values are compared with the normalization of the existing extraction eval (lists as sets, text casefolded). `min_accuracy` is the user's bar for the extractor and the only CI-usable assertion; without it the test suite only reports.

**Agreement first, accuracy from the settled cases.** Agreement needs no ground truth, so the first comparison on real postings works. A comparison writes the unlabelled disagreements to `benchmark/disagreements-<stamp>.json` in the state directory as `{posting, feature, runs: {run id: value}, label: null}`, the postings that differ in most features first, so the user starts with the largest deviations. The user fills `label`, and `--settle FILE` merges the non-null entries into `extraction-labels.json`. Alternative: a checker model settles them, rejected for the extra cost and because it needs its own eval. The file also accepts hand-written labels for spot checks.

**Known bias of the settled labels.** Labels come from disagreement cases, so accuracy on them describes the hard cases, and a case where all runs agree and are wrong is never labelled. The report prints the case count next to accuracy and keeps agreement as a separate figure, and the user can add spot labels by hand.

**DeepEval for the labelled accuracy, own code for the rest.** The decision is to build evals in DeepEval where it reaches, so a CI-style test and the benchmark share one way of working. The accuracy is a custom DeepEval metric (a `BaseMetric` subclass): one `LLMTestCase` per labelled posting, with the posting ID as `input` (never its text, see below), the extracted values as JSON in `actual_output` and the labels as JSON in `expected_output`; the metric scores the share of labelled features that are equal and keeps the per-feature result. The command runs these cases through DeepEval's `evaluate`, and a test module run with `deepeval test run` runs the same cases for the configured extractor and fails below `min_accuracy`. The module (`tests/accuracy_suite.py`) is named without the `test_` prefix, so the default `pytest` run never collects it and only an explicit path runs it, because it makes paid calls; a marker would still import it at collection. Two consequences of DeepEval fixing its folder at import: its pytest plugin, which loads at pytest startup, is disabled for the default run (`-p no:deepeval` in `addopts`; `deepeval test run` re-enables it), and `deepeval test run` needs `DEEPEVAL_CACHE_FOLDER` exported before it starts, which the suite's failure message spells out. Own code stays for what DeepEval does not cover: the run loop, agreement and comparison (they compare runs with each other, so they are no per-case metric), disagreements and `--settle`, cost and latency metering, the records and the Langfuse mirror (DeepEval has no Langfuse integration; the scores are written with the Langfuse SDK). Alternative: all own code, rejected for the first reason in this paragraph; moving the existing evals the same way is #34. `deepeval` becomes a dependency of the backend. Checked with a throwaway run on DeepEval 4.2.3: `evaluate` runs a deterministic `BaseMetric` offline, without a judge model or a network call, and returns a score and a reason per case; `identifier` and `hyperparameters` are stored with the run, so the run ID and the approach parameters travel with the DeepEval result too; DeepEval records neither cost nor latency for our own calls, so the metering stays ours. DeepEval writes the full test cases (input, actual and expected output) to a `.deepeval/` folder in the working directory, and this repository does not ignore it. The test case's `input` is therefore the posting ID, not its text, and the folder is moved into the state directory with `DEEPEVAL_CACHE_FOLDER` (and `DEEPEVAL_RESULTS_FOLDER`), both set before `deepeval` is imported, because the first is read at import time. The boundary check on the state directory covers these files too. DeepEval can also keep runs in a local SQLite file (`DEEPEVAL_LOCAL_STORE=sqlite`); the JSONL records stay the history, since they hold no values.

**Langfuse mirror, JSONL stays the history.** With both Langfuse keys set, a run is also recorded as an experiment (local data, so no hosted dataset is needed) with the run-level scores (accuracy, case counts), the cost per posting and the mean latency. The experiment replays the already extracted values instead of calling the model again, so nothing is paid twice; the real calls are traced through the existing callback of the client. Sending personal data to the configured cloud instance is accepted, so posting text and extracted values may be sent there; the JSONL records still hold neither. Alternative: Langfuse as the only history, rejected because the command would then depend on network and keys, and `--history` on the API. A failure to reach Langfuse is a warning. Checked with a throwaway run on langfuse 4.17.0: `run_experiment` accepts a task that returns the stored values, runs item-level and run-level evaluators locally, and carries cost per posting and mean latency as run-level scores; against an unreachable host it raised nothing and only logged errors. A delivery failure is therefore visible only in the SDK's log, which the warning in the spec relies on. The first real run confirms delivery to the cloud instance.

**Metered per posting.** Per call the benchmark wraps `extract_features` in `metered()` for the cost and takes `time.perf_counter()` around it for the latency. The record stores cost per posting, mean latency and the number of uncosted calls.

**Model construction.** The body of `chat_model` after the settings lookup moves into a function taking (model, base URL, settings), which `chat_model` and the benchmark both call. Alternative: building clients in the benchmark, rejected as a second copy of the provider-prefix and connection rules.

**Decision models as subjects.** The first real comparison showed that `typesafe/jev-1.14.0` cannot be an extractor here: through the router it accepts only `response_format` of type `questions` and answers every other request shape (plain chat, JSON schema, tool call) with HTTP 400, and the extractor's structured output sends exactly those. The existing decision-model eval already calls it the right way (`evals/decider.py`: an OpenAI client, one `choice` question per categorical feature, "unknown" as an extra option). `--role decider` reuses that call as a second extraction function behind the same run loop, record, comparison and Langfuse mirror; the record's `role` says `decider`. Its limit is the question types: it answers categorical features only, so its accuracy counts only the labelled features it answered (a label on a text feature is not a wrong answer of a model that was never asked) and a comparison lists only the features every compared run answered. The call's reported cost reaches the run's meter through `record_call` in `evals/cost.py`, since the call bypasses LangChain's callbacks. The instruction hash of such a run is the hash of its question set. Using Jev as `EXTRACTOR_MODEL` in the app would need the same call in `extract_features`; that is not part of this change.

**Entry point.** `python -m jobadvaisor.evals.extractor_benchmark [--data PATH] [--role extractor|decider] [--model M] [--base-url U] [--limit N] [--compare RUN_ID ...] [--settle FILE] [--history]`. A separate module, not an entry in `EVALS`: those evals return one JSON report each against fixed data, while this one stores runs and compares them. `--limit N` takes the first N postings in ID order, so a cheap trial run and the full run use the same ordering. The state directory (`STATE_DIRECTORY`) lies outside both repositories by default but is configurable, so before any model call the command resolves it and refuses to go on when it lies inside this repository or inside the data repository, naming the setting; the check covers every private output (records, per-run values, disagreements file) and every mode (run, `--compare`, `--history`). The eval CLI checks only this repository for `--out`; the benchmark needs both, since the data repository is a git repository whose history would otherwise receive posting-derived values.

## Risks / Trade-offs

- [Two runs agreeing is not the same as being right] → The report says "agreement" and never "accuracy" for it; accuracy appears only against labels and with its case count.
- [A run on all stored postings costs money] → `--limit` for a trial; the first real runs happen only on explicit go-ahead, and the cost per posting of a trial extrapolates the full run.
- [A single run has no variance estimate; models are not deterministic] → Records accumulate, so repeated runs show the spread; repeated-run variance in one command is left out.
- [The extracted values and the disagreements file hold data from real postings] → Written under the state directory, outside this repository and outside the data repository's git history.
- [A model name made file-safe could collide between two runs of the same second] → The time stamp has second resolution and the command refuses to overwrite an existing run file.
