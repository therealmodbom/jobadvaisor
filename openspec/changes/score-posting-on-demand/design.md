# Design

## Context

See proposal.md for why. Today a score is written only by the pass's `store_scores` node (`triage/graph.py`); the pass's `load` takes only postings without a verdict (`pool.pass_batch`), and `store_scores` keeps the old score of a posting rated while the pass computed, then measures the pass's quality against the scores it just wrote, which was safe only while rated postings were never rescored. The judge (`tools/scoring.score_posting`) reads posting, profile, policy pack and examples; it never reads the extracted features, and the stored `Score` does not hold them. `Runs` (`triage/runs.py`) computes one pass at a time and raises `RunBusyError` for a second one. The correction counter (`pool.counter`) compares every `rating` label since the last pass's start with the posting's current score, whoever wrote it.

## Goals / Non-Goals

**Goals:**
- One scoring path shared by pass and single score, so both send the judge the same input.
- A single score and a pass never write at the same time.

**Non-Goals:**
- A run model, progress polling or checkpoints for single scores.
- A cost figure per click; the cost of a score belongs on a later statistics or benchmark page (#33).

## Decisions

**Passes score rated postings.** `pass_batch` keeps every posting without a readable score, and every posting when the pass rescores; the verdict no longer filters. Its flag `rescore_unrated` is renamed `rescore` everywhere, the wire field `next_pass.rescore_unrated` included, since the old name would now be false; frontend and backend live in this repository and change together. `store_scores` drops the rated skip (`_has_verdict` and the `{"status": "rated"}` result go): a rating given while the pass computes still gets the new score, and the counter, whose window starts at the pass's start, counts that rating after the pass. The quality measure reads the scores before writing, writes the new ones first (so a broken measure still cannot discard paid work), then computes `counter` against the scores it read before. The scoring is fair for rated postings because a posting's own label never reaches its judge (`find_similar_labeled` skips its ID).

**Explicit batch for the eval.** `start_run` takes an optional batch that `load` uses instead of `pass_batch`. `evals/graph_vs_agent.py` passes its held-out postings: its copy keeps the training labels without scores, so the new `pass_batch` would score the training postings too, raising its cost and changing what it compares with the agent.

**Shared scoring step.** The pass's `score` node and the single score both call one function that takes the context and a posting ID, fetches the posting's similar rated postings (its own ID excluded) and calls the judge. The index is synced once per pass and once per single score, before that call. Alternative: a one-posting pass through the graph, with the explicit batch. Rejected: it would record a pass, which resets the counter's window, and run the extractor, a second model call the judge does not need.

**Single score as a plain function.** The single score is one function in `triage/graph.py` that takes the context and a posting ID, runs the gates, the index sync, the shared step and `write_score`, and returns the stored score or raises a refusal naming its reason. It knows nothing of HTTP or of `Runs`: the API route calls it through the `Runs` slot, and a later scoring on intake or import calls the same function. Only the slot and the HTTP mapping live outside it.

**No extraction.** The single score skips the extractor: the judge does not read features, so the score is the same without it and costs one call instead of two.

**Same gates as the pool, by the pool's own check.** The single score calls `pool._blocked` itself, so the rules have one home: a stored held result (refused `held`), then the exclusion rules (refused `excluded`); then `_guard_ruling` for an unchecked posting (checked now when a classifier is configured and refused `held` if flagged, else refused `unscreened`). A checked posting keeps its stored result, so a re-score does not call the guard again, and an excluded one costs no guard call. The pool shows no score for excluded or held rows, so a score computed for them would be invisible there. The UI disables the button for these postings before any click: pool rows already carry `state` `excluded` or `held`; for the unchecked case each row gains `unscreened` (the posting has no guard result), and `GET /pool` and `GET /postings/{id}` gain `screening` from `intake.guard.classifier is not None`, the source the intake answer already uses. Production builds the pass context's guard from the same settings; tests inject the same guard into both. Beside a disabled button sits a visible info icon (lucide `Info`, already a dependency) as a focusable element with an accessible name ("Warum nicht verfügbar?"), its reason in a small popover shown on hover and focus (component state and the `hidden` attribute, so the reason stays reachable through `aria-describedby`; Escape hides it; no tooltip library); the icon carries `aria-describedby` pointing at the reason, since a disabled button cannot take focus.

**Synchronous, in the pass's slot.** `Runs` gets a method that computes a single score in the calling thread while holding the same `_computing` slot a pass holds (key `score:<posting_id>`). A pass started meanwhile gets `RunBusyError`, and so does a single score requested during a pass or during another single score; that also keeps two `LabelIndex.sync` calls from overlapping. `POST /pool/passes` keeps its 409 `pass in progress`; its detail then names `score:<id>`, and the pool already shows "Es läuft schon eine andere Bewertung" for that 409, which fits both cases. The API route is a sync FastAPI route, so it blocks a worker thread for one judge call and nothing else. Alternatives: a separate lock (the two would not see each other), or submitting to the pass executor and waiting (same effect, more code).

**API.** `POST /postings/{id}/score`, no body. 200 answers the `GET /postings/{id}` body plus `counter` and `next_pass`, so the page replaces its data and the pool updates its row and counter from one answer. Errors in the `{error, detail}` shape: 404 unknown posting; 409 with `error` `scoring in progress`, `excluded` (detail names the rules), `held` or `unscreened`; 502 `scoring failed` when the judge, the label index or the content-guard classifier fails (a retry may help); 500 when storing the guard result or the score fails (a retry would not). The UI maps each `error` to its own German message. `scoring in progress` and every error but the API's own 500 `internal error` offer a retry (`scoring failed`, an unreachable server, a proxy's 502 or 504 that carries no API body); the 500 `internal error` of a failed store shows its own message and the button keeps its normal label, because the web-ui spec asks every failure for a way to retry and a disabled button would leave only a reload (a click scores again, at the cost of one judge call); `excluded`, `held` and `unscreened` cannot change on retry, so the UI reloads the posting (page) or the pool row and shows the button disabled with its info icon. That covers a posting the click's own guard check flags.

**Counter.** It stays as is: a score from the button counts like a pass's score, since the posting's own rating never reaches its judge (`find_similar_labeled` skips its ID). No pass is appended, so the window does not move. The counter measures each rating against the posting's latest score, so a later score replaces the verdict of the earlier one: a rated posting that was a correction at 8 is none after a re-score gives it 2, and the counter and `next_pass.rescore` can fall, which can leave the pass button at "(0)" until new corrections arrive. That follows the definition of a correction and is intended; the pass's own stored share is measured against the scores read before it writes, so a correction a button re-score already took back is not counted there either. The window still starts at each pass, so after a pass that rescored rated postings, ratings from before it no longer count, even where they now contradict their new score; an agreement measure over all rated postings is a later change.

**UI.** One hook for the call's state (idle, computing, failed with a message), used by the posting page and by each pool row, and one button component that shows "Score berechnen" or "Neu berechnen" and the computing state. Disabled cases as above. The pool takes the answer's row but keeps its own `exploration` flag, since the posting page's row always carries `false`. The posting page keeps the old score visible, marked "wird neu berechnet", while computing. The page's hint for a posting without a score keeps pointing at the pass, which now scores rated postings too; an unreadable score file keeps showing "Score unlesbar".

**Docstrings.** `start_pass` says postings with a rating are rescored after a correction; now every posting is, and it says so. `pass_batch`, `next_pass`, `start_run`, `load` and `store_scores` are rewritten to the new batch and measure.

**Eval.** No new LLM-backed behavior: the single score and the pass send the judge the same input through the same shared step, which the scoring eval (`backend/jobadvaisor/evals/scoring.py`, precision@k on labels held out by time, demo persona) measures; taking rated postings into a pass changes which postings are scored, not how. `graph_vs_agent` keeps its batch through the explicit batch above. No eval run is needed for this change.

## Risks / Trade-offs

- [A slow judge holds the request open] → the button shows progress; a proxy timeout shows as a failure with retry. Background runs come only if this proves annoying.
- [The first single score after many new ratings embeds them all] → the same happens at a pass's start; embedding costs are small next to a judge call.
- [Two rows pressed quickly] → the second gets `scoring in progress` and its row says so, with retry; the message goes when a pass ends.
- [Leaving the posting page while its score computes] → the page unmounts, the pool has reloaded meanwhile and shows the old score until it reloads again (it reloads whenever it becomes visible), and a row click during that time gets `scoring in progress`. Nothing is lost on the server; the cost is a stale row until the next visit. Accepted: carrying the answer across views would need shared state between two views for one rare sequence.
- [An unchecked posting stays unscorable without a classifier] → the info icon says so; the pass's unscreened question remains the path.
- [A pass after corrections now rescores rated postings too, so it makes more judge calls] → the pass already announces its count before it starts.
